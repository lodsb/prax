# Local LLM benchmark for graph extraction, 2026-09-08

Question: can the Stage 3 extraction run on the desktop's GTX 1070 (8 GB,
Pascal, compute 6.1) instead of the Claude API? Runtime: `llama-cpp-python`
0.3.35 (prebuilt CUDA 12.4 wheel) in the project venv, driver 560.94.
Models: Q4_K_M GGUF quants from bartowski. Every run used the real
extraction inputs: the ontology system prompt (760 tokens), the JSON schema
from `extraction.output_schema`, and `build_input` on the first three PDFs
the selection returns (metadata header plus 12,000 characters of text,
about 2,700 tokens). Grammar-constrained decoding means the schema was
compiled to a GBNF grammar by llama.cpp; the Claude path gets the same
schema through `output_config.format`.

## Speed and memory

| model | VRAM | prompt tok/s | generation tok/s | load |
|---|---|---|---|---|
| Qwen2.5-7B-Instruct | 5.2 GB | 525 | 31.5 | 10 s |
| Qwen3-8B | 6.3 GB | 447 | 28.3 | 11 s |
| Llama-3.1-8B-Instruct | 6.1 GB | 455 | 28.6 | 11 s |
| Qwen2.5-3B-Instruct | 2.5 GB | 999 | 56.4 | 5 s |

Free generation, 256 tokens on a short prompt; prompt processing on the
2,665-token document. Flash attention made no difference on this card.

## Extraction, three documents each

| model | decoding | valid JSON | triples/doc | s/doc |
|---|---|---|---|---|
| Qwen2.5-7B | schema grammar, greedy | 3/3 | 10–11 | 80 |
| Qwen2.5-7B | no grammar, schema in prompt | 0/3 (fences, trailing commas) | – | 53 |
| Qwen2.5-7B | plain JSON grammar, schema in prompt | 3/3 | 9–23 | 85–216 |
| Qwen3-8B (thinking off) | schema grammar, greedy | 0/3 (hit 3,000-token cap) | – | 260 |
| Qwen3-8B (thinking off) | schema grammar, temp 0.6, repeat 1.1 | 0/1 (cap) | – | 266 |
| Llama-3.1-8B | schema grammar, greedy | 0/3 (cap) | – | 246 |
| Llama-3.1-8B | schema grammar, temp 0.6, repeat 1.1 | 1/1 | 26 | 208 |
| Qwen2.5-3B | schema grammar, greedy | 0/3 (cap) | – | 170 |

Under a grammar the 7B model generates at 13–15 tok/s, against 26 tok/s
without one at the same 3,400-token context and 31 tok/s on a short
prompt. The plain JSON grammar is as slow as the schema grammar, so the
cost is the grammar sampler itself, not the schema's size; it also loses
the structure the schema enforces (one document ran to 23 triples, 18 of
them `uses`). The output is roughly 1,100 tokens per document, so decoding
dominates and prompt processing (about 7 s) does not.

The three models that hit the cap were not looping on a token; they kept
adding triples until the limit, because nothing in the schema bounds the
`triples` array and the instruction to be selective does not hold them.
Llama with sampling stopped, but at 26 triples for a paper where Claude's
prompt asks for the handful that matter, eight of them `cites` edges to
bracketed reference numbers. A `maxItems` on the array and a `maxLength` on
`evidence` would end the runaway (both compile to grammar) and are the first
thing a local extractor should add.

## Quality, Qwen2.5-7B

Authors, venue and the proposed method were right on all three papers, and
every `evidence` string is a real quote from the text. Noise per document:
one or two trivial `about` concepts ("audio signals"), one relation with
the wrong domain (`method --about--> concept`, which `store.link` rejects
into the review queue), one "unspecified" venue marked INFERRED, and one
misread relation (`supports` where the paper outperforms). The `unmapped`
list was used as intended (a penalty factor, a dataset it could not name).
Roughly Haiku-class output at a guess; a side-by-side against Claude on the
same three documents is the next measurement once credentials exist.

## Verdict

The runtime works on the Pascal card without a build (the prebuilt wheel
carries compute 6.1), and Qwen2.5-7B-Instruct produces usable, valid
extractions. It is a week of GPU time for the backlog against a $25–125
batch job, so the API remains the default for the bulk run. The local
path is worth keeping as `PRAX_EXTRACT=local` for the incremental trickle
of new documents, for private material, and for the UI "ask" feature,
where a 7B model answering over retrieved chunks at 30 tok/s is fine.

## Line format for the local extractor (same day)

`prax.lineformat` replaces JSON for local models: one tab-separated line
per triple under a hand-written GBNF grammar that bounds the count (20
triples, 5 unmapped) and every field's length. Four runs of Qwen2.5-7B on
the same three papers, `scripts/bench_local_llm.py --lines`:

| variant | s/doc | triples/doc | what happened |
|---|---|---|---|
| positional fields, greedy | 52–97 | 8–20 | valid and bounded, but the document called "paper" and eight `cites [n]` reference numbers |
| plus prompt rules, greedy | 49–82 | 8–20 | greedy loops: one pair of triples eleven times, one unmapped line five times |
| plus dedupe, temperature 0.3, repeat penalty 1.1 | 45–51 | 6–9 | no loops, but sources and targets swapped, types in the relation slot, venue lost |
| plus `key=value` fields | 42–91 | 5–10 | fields right on every line, authors and venue right on all three papers |

Positional fields are the cheapest encoding and the one a 7B model handles
worst: the JSON keys were anchoring the fields, and putting `src=`,
`rel=`, `dst=` back into the lines (eight tokens per triple) restored
that. What the keyed format gives up against JSON is breadth: about half
the triples per document, mostly fewer `about` concepts, with no wrong
directions in exchange. Per-document time is the same as JSON because the
model fills the smaller budget more slowly, and the grammar sampler still
halves the token rate.

Guards that came out of these runs and apply to every extractor: names
that are only a reference number are rejected in `apply`; a local model's
"paper" / "this paper" is mapped to the document title; repeated triples
and unmapped items are dropped by the parser and counted in `usage`.
Still open: the model sometimes writes keys inside a name
(`phase unwrapping(dst_type=method)`) and always fills the unmapped quota.

## Claude models on the same three papers (2026-09-09)

With a key in place, Opus 5, Sonnet 5 and Haiku 4.5 ran on the same
three papers through the JSON path (triple cap 40 at the time):

| model | triples/doc | s/doc | per document | notes |
|---|---|---|---|---|
| Opus 5 | 20 | 27–41 | $0.103 | claims typed as claims, the proposed method as its own node; failed on paper 3 every time with a generic 400 during generation |
| Sonnet 5 | 16–20 | 40–63 | $0.040 | close to Opus in structure, more reference-number papers in unmapped; one empty answer on paper 3, fine on retry |
| Haiku 4.5 | 21–25 | 36–41 | $0.015 | broad: up to ten `about` concepts, some `cites` pointing at methods |
| Qwen2.5-7B local | 5–10 | 42–91 | 0 | authors and venue right, little else |

Output is 2,000–3,000 tokens per paper, three times what the dry run
assumed, so the projections became Haiku $64, Sonnet $170, Opus $436 for
the library as a batch. Sonnet 5 with the cap lowered to 20 was chosen;
the 21-document trial then cost $0.034 per document synchronously (about
2,500 output tokens), 181 edges and 38 review items, and the batch
projection for the remaining 7,955 documents is about $135.

## Setup notes

* `CUDA_PATH` on this machine points at a CUDA 10.2 toolkit; the wheel's
  loader adds that directory, harmlessly, and needs `cudart64_12.dll` and
  `cublas64_12.dll` from the `nvidia-cuda-runtime-cu12` and
  `nvidia-cublas-cu12` wheels instead.
* The loader calls `ctypes.CDLL(..., winmode=0)`, so on Windows the DLL
  dependencies must be on `PATH`; `os.add_dll_directory` is not enough.
  `prax.local_llm.llama_class()` prepends the venv's `nvidia/*/bin` and
  `llama_cpp/lib` folders before importing.
* Models live in the Hugging Face cache (`~/.cache/huggingface/hub`),
  17 GB for the four above.
* Benchmark script: `scripts/bench_local_llm.py`.
