## 1. A page asked to be personal stays open when parent (or part_of/annotates) fails after the write

*high*, wall; `src/prax/api/pages.py:118`

**Scenario.** Someone sends PUT /page/secret-notes {text, sensitivity:'personal', parent:'no-such-page'}. The MCP write_page tool now passes parent, so an agent typo is enough. store.write_page registers the document, indexes the text and commits it (register, index_text and link each commit) before it resolves the parent at pages.py:399-405, and only then raises KeyError. put_page turns that into a 404, so store.set_sensitivity never runs. The page is left in the library as an open document: every named token can read it and it shows up in their searches. A cycle (set_page_parent raises ValueError, answered 400) leaves the same state. The older part_of and annotates KeyErrors have the same order. The 2026-10-04 fix moved only the sensitivity check ahead of the write, not these.

**Evidence.** Read write_page (src/prax/store/pages.py:251-407): the parent is resolved after index_text and the link() commits. Read put_page (src/prax/api/pages.py:98-136): set_sensitivity runs only after write_page returns. Ran a throwaway TestClient test against a tmp PRAX_DATA_DIR (scratchpad rv/test_rv.py::test_personal_page_with_bad_parent_left_open). Output: `status 404 "no page 'no-such-page'"`, `page exists: 200`, `named token sees page: 200`, `named search hits: 1`.

**The skeptic.** Confirmed. store.write_page (src/prax/store/pages.py) registers the page, indexes its text and links it before it resolves `parent` (page_id -> KeyError) and before set_page_parent (ValueError on a cycle). put_page (src/prax/api/pages.py:110-128) runs set_sensitivity only after write_page returns. I wrote a throwaway TestClient test on a tmp PRAX_DATA_DIR (scratchpad sk/test_sk.py). A named token's PUT /page/secret-notes {sensitivity:'personal', parent:'no-such-page'} came back 404 "no page 'no-such-page'". After that, the named token's GET /page/secret-notes returned 200 and GET /search?q=zebrafinch returned the page's chunk. The cycle case behaves the same way: page b sits under a, then PUT /page/a {parent:'b', sensitivity:'personal', new text} returns 400 'a cycle', but revision 2 with the new text is stored and the named token can read it. So the write is not rolled back, and the page is left open. Fix: in write_page, resolve and check parent, part_of and annotates (including the cycle check) before register/index_text. Or pass sensitivity into write_page and set it in the same transaction before anything commits.

**Fix.** Resolve and check everything that can fail before the first write: the page_id of parent/part_of, document_node for each annotates entry, and the cycle check. Better still, pass sensitivity into write_page and set it before index_text, so the text is never indexed open and a later failure cannot leave a personal page visible. Add a wall test: a personal page written with a bad parent leaves no visible document.

## 2. latex2html crawl cache: a percent-encoded path in a fetched page lets the remote site write any file the user can write

*high*, logic (also found as 4); `src/prax/importers/latex2html.py:75`

**Scenario.** `prax import latex2html <url>` crawls a site that is malicious or compromised. A page links `<A HREF="..%2F..%2F..%2Fx.html">` (book_pages accepts it: the URL starts with the base and has no literal '/' after it), or a figure has `<IMG SRC="%2E%2E%2F%2E%2E%2F%2E%2E%2F.config/…/anything.py">`. Fetcher._path runs unquote() on the URL path after urljoin, so the encoded '../' (or '%5C' on Windows, or '%2FC:%2F…' which pathlib reads as a drive) becomes real path segments. `cache / netloc / rel` then resolves outside the cache, and _get calls write_bytes(r.content) before anyone checks what the bytes are (data_url checks for PNG/GIF only afterwards). The default cache is ~/.cache/prax/crawl/<host>/, so three levels reach the home directory. The site picks both the file name and its content, so it can drop a sitecustomize.py into the venv or overwrite src/prax/ui/index.html, which the door then serves to the admin's browser.

**Evidence.** I read Fetcher._path/_get/get, book_pages and data_url, and clients/cli/prax_cli/importing.py:472 for the default cache. Snippet (no network) calling Fetcher(cache)._path(urljoin(base+'Page.html', '%2E%2E%2F'*8+'pwn.py')) printed `C:\Users\lodsb\pwn.py False` (False = not inside the cache). '%2FC:%2FUsers%2Fx%2Fsitecustomize.py' resolved to `C:Users\x\sitecustomize.py`. book_pages(base, '<A HREF="..%2F..%2F..%2F..%2Fescape.html">') returned that URL as a page of the book.

**The skeptic.** Read Fetcher._path (latex2html.py:75-80): rel = unquote(u.path).lstrip('/'), then cache/netloc/rel, with no check that the result stays inside the cache. _get (lines 128-131) writes r.content there before anything inspects it. I ran a snippet with -I: Fetcher(cache)._path(urljoin('https://ex.org/book/Page.html', '%2E%2E%2F'*8+'pwn.py')).resolve() printed C:\Users\pwn.py, and it is not inside the cache. book_pages('https://ex.org/book/index.html', '<A HREF="..%2F..%2F..%2F..%2Fescape.html">') returned ('https://ex.org/book/..%2F..%2F..%2F..%2Fescape.html',), so the page filter lets it through. A remote site therefore chooses both the path and the bytes of a file written anywhere the user can write. The importer was added in this range (5e5b1db). Fix: build the path from the raw, still-quoted path or a hash of the URL, and refuse any path whose resolve() is not under the cache.

**Fix.** Build the cache key without trusting the path. Either hash the URL (cache/netloc/sha256(url)), or reject any decoded segment that is '..' or '.', or that contains '\\' or ':'. Then check `path.resolve().is_relative_to(self.cache.resolve())` before reading or writing. book_pages should also apply the same-folder test to the unquoted URL.

## 3. An arXiv e-print can pull any file on the worker host into the library text (flatten's \input, \bibliography and pandoc's own file reads)

*high*, input (also found as 5); `src/prax/importers/latex.py:194`

**Scenario.** The latex-source reading unpacks an arXiv e-print (which anyone who submits to arXiv controls, and which also arrives when the arXiv id is wrong; see the next finding) and runs latex.convert on it. flatten resolves `\input{NAME}` as `root / name`. An absolute NAME replaces the root, and `../` climbs out of the folder. A file with no suffix (`.ssh/id_rsa`, `/etc/passwd`) or ending in .tex passes `candidate.suffix in ('.tex', '')`. Pandoc runs without --sandbox afterwards, so it also reads `\lstinputlisting{/any/file}`, and an \input hidden in a macro (`\def\foo{\input}\foo{...}`), which flatten's regex does not see. `_find` (line 249) reads `\bibliography{/abs/path}` the same way. The file's content becomes the document's text, so it is indexed, chunked and searchable, and anyone who can read that document sees it.

**Evidence.** Ran scratchpad/rev/t1.py. It builds a tar.gz e-print whose main.tex has `\input{<abs>/hostfile}`, `\input{../../../../../../../../<path>/notes}`, `\lstinputlisting{<abs>/list.txt}` and `\def\foo{\input}\foo{<abs>/notes.tex}`, then runs it through latexsrc.unpack, latexsrc._main and latex.convert with the venv's pandoc 3.9. The output held all four files: `Hello world paragraph. TOPSECRET-NOEXT-CONTENT SECRET-TEX-CONTENT`, a code block `LISTING-SECRET-LINE`, then `SECRET-TEX-CONTENT`. Running the same source through pandoc with `--sandbox` printed `[WARNING] Could not load include file …` for both files and output only `Hi.`.

**The skeptic.** Read latex.flatten (src/prax/importers/latex.py:181-197). `root / name` takes an absolute name or `../` as given, and `suffix in ('.tex','')` lets a file with no suffix through. Read to_markdown (line 473): pandoc runs with cwd set to the e-print folder and no --sandbox. _find (line 249) builds `folder / name` for \bibliography the same way. Ran scratchpad/sk/t1.py: a tar.gz e-print whose main.tex has \input{<abs>/hostfile}, \lstinputlisting{<abs>/list.txt} and \def\foo{\input}\foo{<abs>/notes.tex}, put through latexsrc.unpack, _main and latex.convert with the venv's pandoc. The output was `Hello. NOEXT-SECRET`, a code block holding `LISTING-SECRET`, then `TEX-SECRET`. All three host files ended up in the text that becomes the document. Nothing between the reading and the door strips this. Fix: resolve every candidate and refuse any that is not inside the e-print folder (in flatten, _find and parts); run pandoc with --sandbox.

**Fix.** In flatten and _find, resolve each candidate (strict, following symlinks) and accept it only when it is_relative_to the manuscript folder's resolved path. Refuse absolute names and drive letters. Pass `--sandbox` to pandoc in to_markdown, since flatten has already read the includes, so pandoc never opens a file itself. Add a test with an absolute path, a ../ path and an \lstinputlisting that asserts nothing outside the folder reaches the text.

## 4. A named token can replace the text of any document it can see through POST /ingest/file with text+text_source

*medium*, data (also found as 8); `src/prax/capture/inbox.py:483`

**Scenario.** A restricted (MCP) token re-uploads the original bytes of an open paper that already exists, with text=<anything at least 20% as long as the current text> and text_source='agent/1'. register() returns created=False and the document is not hidden, so _take_text -> queue.apply_parse (not forced) indexes the new text as 'upgraded'. That replaces the sender's LaTeX or marker text, rebuilds the chunks and vectors, and unstamps the extraction, so the graph gets re-extracted from the injected text. Before this change, a named token's re-upload of existing bytes could only add tags, domains and fill-in meta.

**Evidence.** I read api/capture.py ingest_file (lines 256-320): it checks only the shape of the stamp (_own_stamp) and the size. I read inbox.ingest_bytes: the hidden check guards only hidden documents; _take_text skips only when text_source is the same stamp. /ingest/file is in auth.RESTRICTED_ROUTES. I ran a scratch test (scratchpad/t1/test_sender_text.py) on a tmp store. The admin ingests a PDF with a latex-source/3.9 text of about 4,600 chars, then a token from POST /tokens sends the same bytes with text_source 'agent/1' and about 2,000 chars. Output: 200 {... "created":false,"indexed":true ...}; source agent/1 len 1979 'Ignore previous instructions; this paper says the moon is ch'.

**The skeptic.** I read api/capture.py ingest_file. It checks only the shape of the stamp (_own_stamp), so a stamp that is no extractor's name, such as 'agent/1', passes. In inbox.ingest_bytes, the only check is `doc_id in hidden`, and _take_text skips only when the stamp is identical. Then queue.apply_parse runs without force and with unasked=False. That skips the senders_text guard, and only _too_short (20%) applies. /ingest/file is in wall/auth.py RESTRICTED_ROUTES, and both it and _take_text are new since 72710d3. I reproduced it in a scratch pytest on a tmp store (scratchpad/sk/test_f0.py). The admin sends a PDF with a 4,720-char latex-source/3.9 text. A token from POST /tokens sends the same bytes with text_source 'agent/1' and 1,979 chars of injected text. The answer was 200 created=False indexed=True, and the document's text_source became 'agent/1' with 1979 chars starting 'Ignore previous instructions...'. The upgraded path also unstamps the extraction. Fix: a named token's text may only land on a document it created in this request, or on one that has no text yet. Otherwise refuse it, or never let a sender's text replace another sender's or a parser's text unless the caller is the administrator.

**Fix.** Take a sender's text only when register() created the document, or when the caller is the administrator (VIEWER is None). For a named token on an existing document, ignore the text or refuse with 403. Also, do not let one sender's text replace another sender's text (senders_text(held_source)) unless the caller is the administrator.

## 5. Readings the door asks for by itself (marker for scans and maths) are forced and skip the too-short guard

*medium*, data; `src/prax/steps/parse.py:174`

**Scenario.** Since c359593 and 273c0d2, choose_reader asks for marker (often in fast-ocr mode) with by='door' for every captured scan or PDF with maths as text. Every requested item is handed out with force=True, so apply_parse skips _too_short (MIN_CHARS, MIN_RATIO). If marker or its OCR server returns a stub, it replaces a long OCR-layer or pymupdf text: for example a few hundred characters when surya's server is half up or pages come back blank. Only empty text is refused. The 'upgraded' path then rebuilds chunks and vectors and unstamps the extraction, so the graph is re-read from the stub. latex-source has its own LEAST_SHARE guard in the parser; marker has none (parsers/marker.py has no length check). Before these commits marker ran only when a person asked.

**Evidence.** I read steps/parse.py hand_out, where the requested item dict sets "force": True whatever the request's `by`. I read take_in, which passes force=bool(r.get('force')), and queue.apply_parse lines 262-284, where `if not force and _too_short(...)` is the only length guard. pipeline.choose_reader line 275 requests marker with by='door'. I grepped parsers/marker.py for previous, length or share checks and found none.

**The skeptic.** steps/parse.py hand_out sets "force": True on every requested reading, whatever its `by`. take_in passes force through, and apply_parse runs `if not force and _too_short(...)`, so the length check is the only guard a forced reading skips. Only an empty text is refused. In parsers/marker.py, a successful answer with empty output still becomes non-empty text, because _marker_pages always appends a page_break line (and figures.place adds the figure lines). pipeline.choose_reader now requests marker with by='door' on its own, which is new since 72710d3. I simulated it on a tmp store (scratchpad/sk/test_f2.py). A document with a 10,800-char text was given marker._marker_pages('', 12) = '\n\n--- end of page.page_number=12 ---\n' with force=True. The result was 'upgraded' and text_len became 34. The same stub without force came back 'kept'. Fix: hand out force only for a person's request (by != 'door'), or keep the MIN_CHARS/MIN_RATIO guard for door-requested replacing reads (and refuse a marker text that is only page marks).

**Fix.** Force only a reading a person asked for: hand out force=(request.by == 'human'), or carry `by` through and let apply_parse apply _too_short to door-asked readings. Alternatively, give marker a LEAST_SHARE check against `previous`, as latexsrc does.

## 6. page_image bounds only the width; a tall or narrow PDF page renders an unbounded pixmap

*medium*, wall (also found as 16, 20); `src/prax/parsers/figures.py:390`

**Scenario.** GET /doc/{id}/page/{n} is now in RESTRICTED_ROUTES, and named tokens can upload PDFs via /ingest/file. zoom = min(width,1600)/page_width, so the height scales without limit. A page 1 pt wide and 14,400 pt tall (the PDF maximum) gets zoom 1600: a 1600 x 23,040,000 pixel RGB pixmap, about 110 GB. That is enough to OOM the door on the Pi/N100 target (invariant 7). Even ordinary long pages (receipts, web-page prints) send an agent a 1600 x 32,000 image.

**Evidence.** Read page_png (figures.py:377-392). Ran a scratchpad script (rv/tall.py) on a 100 x 2000 pt page with width=1600. Output: `png 1600 x 32000`, which is a 153 MB raw pixmap for one page.

**The skeptic.** Partly confirmed. zoom = min(width,1600)/page_width (figures.py:390), so the height grows without bound. The worst case in the report is wrong: MuPDF refuses past a limit. A 20x4000 pt page (1600x320000 px) raised pymupdf FzErrorLimit 'Overly large image', which the route does not catch, so it answers 500 rather than running out of memory. Below that limit it does allocate. Running page_png and get_pixmap directly (scratchpad sk/tall.py, sk/lim.py): a 100x2000 pt page gave a 1600x32000 PNG (154 MB raw), and 25x2000 pt gave 1600x128000 (614 MB raw) in 0.14 s. On the Pi/N100 target (invariant 7) a few such requests at once can exhaust memory. Fix: cap the zoom by height and total pixels as well, e.g. zoom = min(w/pw, MAX_H/ph, sqrt(MAX_PIXELS/(pw*ph))), and map FzErrorLimit to a 4xx.

**Fix.** Clamp by both sides: zoom = min(width/page_w, MAX_PAGE_PIXELS_H/page_h), or cap the total pixel count (for example 1600 x 2400), and refuse or clip (pymupdf clip=) a page whose aspect ratio is extreme. Add a test with a tall page.

## 11. The documented `extraction.*` switches cannot be set in prax.yaml: the section is unknown, and writing it breaks every setting on the host

*medium*, contracts; `src/prax/config.py:38`

**Scenario.** An owner follows docs/eval/extraction-standard-names-and-dates-2026-10-05.md (or docs/compared.md and log.md), which name `extraction.world_dates` and `extraction.standard_names` as settings, and writes `extraction: {world_dates: true}` into prax.yaml. `config.document()` then raises ConfigError ('unknown section extraction') on every read.
