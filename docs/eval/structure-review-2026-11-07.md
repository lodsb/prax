# The structure review of 2026-11-07: reuse and modularity over all of src

A quality review of the whole tree, not of a range of commits: the owner
asked why `src/prax` is 81,000 lines (the store 31,000) and whether reuse
and modularity were done properly. Five reviewers read it in parts (the
store's documents and retrieval; the rest of the store; the door, capture,
steps and host; the graph, parsers, importers and answering; the concepts
spread across all of it), each with a skeptic who re-checked every
finding. 56 findings were confirmed and 4 refuted.

## What the size is

| | lines |
|---|---|
| `src/prax` | 80,993 (72% code, 13% docstrings, 3% comments, 12% blank) |
| of it `store` | 30,911 |
| of it the store's six `__init__` re-export lists | 1,934 |
| blocks of 8 lines or more that occur twice | 294 |

Copying is rare. What the review found is a concept with several owners,
each written its own way: a document's meta read and written by hand at
some 70 places, the entity a name means found by eight queries, an edge
ended by seven functions, a step's "tried" recorded in four shapes, store
errors turned into HTTP codes by hand about 140 times. All the fixes
together would remove 2,000 to 3,000 lines. The cost of leaving them is
the bugs below, which came from exactly that.

## Fixed the same day

Each with a test that fails on the code before.

1. **A clean-up's restore rewrote history.** `restore_set` set `valid_to`
   back to NULL on the edges it had ended, so `held_at` and `changes` said
   they were never ended (invariant 8). The clean-up now ends them under
   its run (`end_edges`) and the restore states them again
   (`restore_run`); a clean-up from before records its old list of ended
   edges as the run's endings first. The clean-up moved from
   `documents.library` to a part of `repair` of its own (`cleanup`), after
   the graph in the store's order. Finding 2.
2. **A rename did not survive the night.** `rename_entity` wrote the new
   name and no label, and the `names` pass rebuilds the name from the
   labels: a retitled document's node, a renamed page's node and the heal
   pass's name repairs went back to the old name. It now keeps the old
   name as a `was` label and prefers the new one, under a run
   `unmerge_run` takes back (`labels._relabel`, which `rename_person`
   shares). `retitle` was split: the document's half stays in
   `documents.meta` (`_retitle_document`), the node's half moved to
   `graph.labels`, which finds the node with `document_node` (it was
   `paper` only) and renames or merges it through `rename_entity`.
   Finding 7, and wider than it said.
3. **A step that failed on a text never tried its replacement.** The
   genres, dates, summaries and titles steps mark a document they got
   nothing from (`meta.<step>_tried`) and pass it by; nothing cleared the
   mark when a new read replaced the text. `index_text` now clears
   `TRIED_ON_TEXT` when the text's hash changes. Finding 1, in part; one
   shape for all four is still to do.
4. **A new read dropped every formula reading.** `carry_readings` keyed
   readings on figure references only. It now keys each on what it is
   under (`figures._anchor_of`: a figure's hash, or an equation's LaTeX
   with the spacing collapsed). This affects the 305 formula readings
   asked for on 2026-11-06. Finding 6.
5. **Claude's cost reached the ledger only from the vision reading.**
   `ClaudeRuntime.chat`, and an OpenAI-shaped runtime with a key, now
   record what they used (`prax.ml.usage`); `Pass.post` carries it home
   with every step's results as `spent`, and `work.take_in` writes it.
   The typing step's own noting went, so nothing is counted twice.
   Finding 5.
6. **The door's own readings ran on a priced API.** `pipeline._free`
   counted any OpenAI-shaped model as free; it reads `ModelSpec.paid`.
   Finding 21.
7. **The communities pass gave a dissolved region's id to a new one.** It
   uses `id_marks` (migration 59) as face groups and event candidates do,
   through `base.first_fresh_id` and `base.mark_ids`, which all three call
   now. Finding 18.
8. **The store called an exited process alive** on Windows while its
   handle was held, which kept a dead worker's job row running.
   `store._pid_alive` asks `prax.host.process._alive`. Finding 46.
9. **A page's revision, move or split and a project's sync ended edges
   with no record**, so `restore_run` could not undo them.
   `_invalidate_edge` records the ending under the run it is given, and
   the four callers give theirs. Finding 4, in part.
10. **The wall: a derived fact named an entity its premises hide.** A
    rule edge whose premises are open by sensitivity carries no document;
    the checks of whether an entity is spoken of where a viewer may look
    (`_said_openly`, `_open_label`, `_visible_ids`) took it as open, so a
    token limited to some modules found an entity only documents outside
    them speak of. They leave rule edges out (`edges._ASSERTED`): every
    end of a derived fact is an end of a premise, which carries its own
    document. Finding 39.

### 1. Four mechanisms record that a step did or tried a document, and they disagree on when to try again

*high, store-docs; a stage with a data migration; about 80 lines.*

- **Sites.** (a) meta `X_tried` markers, each with its own writer: genres.py:283 genres_tried, meta.py:221 published_tried, meta.py:357 summary_tried, capture/pipeline.py:116 mark_tried (titles_tried). meta.py:848 sections_needed filters on `$.sections_tried`, which nothing writes and DocumentMeta does not declare, and its `untried_only` parameter is never passed. (b) text_hash stamps: meta.py:256 world_dates, meta.py:845 sections, readings.py:287/378/453 and maintain.py:1017 quality. (c) version stamps `coalesce(json_extract(meta,'$.K.v'),0) < ?`, 12 sites in photos.py:47-260 and graph/geo.py:62-110. (d) the readings table: readings.py:788 tried_on_this_text, keyed on parsed_at. Each has its own `_needed`/`_due`/`_counts` query: dates_needed, world_dates_needed, sections_needed, genres_needed, photos_due, faces_due, places_due, face_vectors_due, uncounted_pages, figures_to_read.
- **Evidence.** (a) never resets when the text changes: a document whose genres or date failed on a bad OCR text is never asked again after marker re-reads it. (b) and (d) do retry on a new text, and the commit log for 0da6ba4 and 2093c44 spent two nights adding that behaviour to the readings. photo_counts and face_counts (photos.py:92,240) are called only by tests, and the review of 2026-10-28 already found their 'due' and 'counts' conditions drifting apart.
- **Why here.** Every new worker step (docs/PLAN.md keeps adding them) picks one of the four shapes by copying, which decides whether it loops forever, never retries, or retries on a new text. The bug is fixed per step, as the readings were.
- **Fix.** One stamp per step in meta, `meta.steps.<step> = {v | text_hash, outcome, run, why, at}`. One `_due_sql(step, *, by='version'|'text', retry_on_new_text=True)` builds the due and count predicates, and one `_mark(con, doc, step, outcome, run, why)` replaces the four `_tried` writers. The readings table stays the queue for readings but uses the same 'on this text' rule. A migration moves the existing `_tried` and `.v` keys.
- **Risk.** The UI and the Jobs page read today's keys (photo.v, faces.v, sections.text_hash, genres_tried). The migration must move them, and the expression indexes on meta paths (migrations 10 and 32) must be rebuilt for the new paths, or the due scans lose their indexes.
- **Checked.** Confirmed. genres_tried, published_tried, summary_tried and titles_tried (capture/pipeline.py:116) are popped only when their own step succeeds (meta.py:214, 342). Nothing in documents/text.py (index_text) clears them, so a document that failed on a bad OCR text is never offered to those steps again after a re-read. Sections, quality and the readings retry on a new text_hash (meta.py:845, readings.py:788). `$.sections_tried` (meta.py:848) is never written and is not in DocumentMeta. `untried_only` on sections_needed is never passed: writing.py:248 and test_sections use the default. photo_counts and face_counts are test-only. This is the place the next 'never asked again' bug will come from. A unified per-step stamp is a real simplification, but it needs a data migration, so it costs more than the line count suggests. ~200 saved is optimistic; ~80 is net of the new helper.

### 2. Undoing a run over documents is built four ways, and retire/restore reopens edges in place instead of using edge_endings

*high, store-docs; a day; no migration; about 40 lines.*

- **Sites.** library.py:39 retire_document ends edges with a raw `UPDATE edges SET valid_to` (line 80) and no edge_endings row. library.py:492 retire_set keeps the ended ids in meta.retired.ended. library.py:551 restore_set reopens them with `UPDATE edges SET valid_to = NULL` (line 569). media.py:291/320 decide_media and undo_media keep the old value in meta.sensitivity.before. The graph's mechanism is graph/edges.py:523 end_edge, :555 end_edges (edge_endings) and :761 restore_run, which restates as new edges and leaves the ended edge ended. graph/labels.py:542 unmerge_run, graph/events.py:583 and graph/versions.py:373 add their own undos.
- **Evidence.** restore_run's docstring: 'The ended edge stays ended: when prax held what is history.' restore_set does the opposite and rewrites valid_to, so `held_at` and `changes` for the period between retire and restore report that the edges were never ended. The cause is the package ORDER: documents comes before graph, so library.py cannot call end_edges and writes the SQL itself.
- **Why here.** The next bulk operation on documents (the cleanup rules, a de-duplication pass, a media decision) picks one of these. Invariant 8's record time is kept by only one of them. A fix to edge ending (batching, the END_BATCH lesson of 2026-10-18) has to be made twice.
- **Fix.** Move the edge-ending core (end_edges' SQL and its edge_endings insert) down into base, or put retire/dedupe/restore after graph in a part of their own. Then retire_document ends edges with a run and restore_set calls restore_run. Document-level 'before' values (sensitivity, domains) go into one small run-record helper rather than per-field `before` keys. Hand the reopen-in-place semantics to the safety review as an invariant-8 question.
- **Risk.** restore_set currently makes the same edge ids live again; restore_run creates new ids. Anything holding an edge id across a restore (review items, edge_premises, pages' annotates) would see a new id.
- **Checked.** Confirmed. retire_document ends edges with a raw `UPDATE edges SET valid_to = {_NOW}` (library.py:83) and writes no edge_endings row and no run. retire_set records the ended ids in meta.retired.ended (library.py:519). restore_set reopens them in place with `UPDATE edges SET valid_to = NULL` (library.py:569-573). That erases the record time of the ending, contrary to restore_run's 'the ended edge stays ended'. As a result, held_at/changes over the retired period are wrong after a restore. The ORDER explanation holds: documents precedes graph, so library.py cannot call end_edges. Moving the edge-ending core down, or moving retire/restore after graph, is the fix. The invariant-8 question belongs to the safety review. ~40-60 lines.

- **Sites.** name to entity: graph/edges.py:166 _entity_id (exact name, does not follow canonical, then a label only one entity carries), graph/lookups.py:81 entity_answering (the same lookup but follows canonical: a copy that has already drifted), graph/labels.py:411 entities_by_label (label only, follows canonical, test-only), graph/traversal.py:228 senses (name is case-sensitive, label NOCASE), graph/traversal.py:722 _entity_ids (name NOCASE, adds the alias group), retrieval/query.py:155 _named_as, repair/graph.py:945-947 _CARRIER/_HOLDER, pages/writes.py:262 _rename_page, documents/meta.py:422-427 set_title. Canonical-of inline (canonical_entity at edges.py:589 exists, but only tests call it): faces.py:606, imports.py:432, labels.py:271, naming.py:316, people.py:51, pictures.py:32. Alias group (id = ? OR canonical_id = ?): edges.py:141 _said_openly, people.py:47 _group, pictures.py:30 and :48 _with_aliases, traversal.py:252, traversal.py:745.
- **Evidence.** _entity_id and entity_answering hold the same 15-line label fallback word for word; they differ only in whether the exact-name hit follows canonical_id. senses matches `name = ?` case-sensitively while _entity_ids uses `name = ? COLLATE NOCASE`, so the same walk input reaches different entities depending on the entry point. find_edges (edges.py:485) matches edges by the literal entity name only, while link resolves through labels. So the 'already live?' check that 14 callers make before link misses an edge that was written through a label (Olivenöl stored under 'olive oil').
- **Why here.** Identity is the plan's open thread (docs/stratification.md step 5: entities.name becomes a display label, and 'to be done whole'). The next bug of the 'two senses / a fold answering for itself' kind (migration 23's note in entities_by_label) will come from whichever copy was not updated.

Delete the inline copies. Decide once whether an exact-name hit on a folded row returns the row or its survivor. Today _entity_id returns the row on purpose, so edges are written to the row they name; keep that behaviour and document it in one place.
- **Risk.** Behaviour changes where copies disagree: senses would become case-insensitive, find_edges would start finding label-resolved edges, so some importers' 'existing' counts rise and they write fewer duplicates. Walk results and tests that pin today's case behaviour may move.
- **Checked.** Confirmed. edges.py:165 _entity_id and lookups.py:81 entity_answering share the label fallback word for word and differ only in COALESCE(canonical_id, id) on the exact-name hit. traversal.py:228 senses matches `name = ?` case-sensitively, while traversal.py:722 _entity_ids uses NOCASE, so the two walk entry points answer the same input differently. 'SELECT COALESCE(canonical_id, id) FROM entities WHERE id = ?' is inlined at faces.py:606, imports.py:432, labels.py:271, naming.py:316, people.py:51 and pictures.py:32. canonical_entity (edges.py:589) does the same thing, but only tests/test_resolution.py:105 calls it. The alias-group query is repeated at people.py:47, pictures.py:30 and traversal.py:252/745. One owner would cut about 60-90 lines, not 120: each inline copy is only 4-6 lines. The real cost is the case-folding drift. Risk: the exact-name hit on a folded row is deliberate in _entity_id, so it must be kept.

### 4. Ending an edge: five public functions plus three private wrappers for one act, of which only some can be undone

*high, store-rest; a few hours plus tests; about 60 lines.*

- **Sites.** UPDATE edges SET valid_to at 7 sites: edges.py:534 end_edge, :576 end_edges, :613 _invalidate_edge, :654 retire_reading, :768 restore_run (re-does retire_run), :847 retire_run, labels.py:606 unmerge_run (re-does retire_run(run=)). edge_endings INSERT at 3 sites (:540, :579, :716). Wrappers: repair/common.py:90 _invalidate (len(end_edges)), rules.py:355 _end, edges.py:713 record_ending (no caller anywhere: dead). 'Correct an edge' (end it, link the corrected one, then record_correction) is written out at repair/graph.py:479-492 and :664-678, and differently at graph/worlddates.py:514 (end_edge(corrected_by=)). invalidate_edge's successor/confidence/evidence/producer/run parameters exist for that same act but only tests/test_resolution.py:273 uses them.
- **Evidence.** Page and project edges end through _invalidate_edge, which records no edge_endings: pages/writes.py:446, pages/splits.py:397, pages/moves.py:216, capture/projects.py:405. Repairs end through end_edges(run=), which records them. So restore_run can undo a repair but never a page move or a project sync, although both are 'runs'. In the correction pattern, end_edges, link and record_correction each commit separately (three fsyncs). A failure between them leaves an ending with no corrected_by, which why then reports as a plain retirement. _invalidate_edge raises KeyError when the edge is no longer live; end_edge returns False. Callers must know which one they hold.
- **Why here.** Invariant 8 promises that 'a repair that ends edges records them … so restore_run undoes it whole'. Every new pass picks one of five doors, and two of them break that promise without a sign. The `edge_endings` schema has already grown twice (migrations 44, 46); with eight writers, each growth means another hunt.
- **Fix.** Keep two functions. end_edges(ids, *, run, corrected_by=None) is the only UPDATE and the only endings insert, with one return shape. correct_edge(old_id, new: Edge, *, run, copy_evidence=True) ends, links and records in one transaction. retire_run, retire_reading, restore_run and unmerge_run select ids and call end_edges. Delete record_ending, the successor parameters of invalidate_edge and the _invalidate/_end wrappers. Give page writes a run (they already compute f"{slug}@{revision}") so their endings are recorded.
- **Risk.** retire_reading and retire_run are set-based UPDATEs; turning them into select-then-end_edges costs a second statement on large producers (batched at 500). Recording endings for page edges adds edge_endings rows that restore_run will then act on. Check that restoring a page run is wanted.
- **Checked.** Confirmed. end_edge (edges.py:521), end_edges (:552), _invalidate_edge (:600) and retire_reading (:635) each write their own UPDATE edges SET valid_to. Only end_edge and end_edges record edge_endings, and record_ending (:713) has no caller anywhere. Page and project endings use _invalidate_edge, which records no ending, at pages/writes.py:446, splits.py:397, moves.py:216 and capture/projects.py:405, so restore_run cannot undo them. invalidate_edge's successor parameters are used only at tests/test_resolution.py:273. The correction act (repair/graph.py:479-492 and :664-678) is _invalidate, then link, then record_correction: separate commits that a failure can leave half-done. _invalidate_edge raises KeyError where end_edge returns False. I count about 60 lines saved, not 80, because restore_run and unmerge_run keep their own selects. Risk: the bulk retire_reading UPDATE is set-based for speed and should stay a single statement, or call end_edges with ids.

### 5. Claude is called four ways, and only one of them records what it cost

*high, logic; half a day; tests for the extractor's batch params and the budget test need adjusting; about 60 lines.*

- **Sites.** 4 client builders and 3 ways of reading token counts: models.py:733-783 ClaudeRuntime.chat (timeout and 3 retries; keeps input/output tokens only, drops the cache fields, never calls ml.usage.record; no images); graph/extraction.py:568-646 ClaudeExtractor (its own client at :589, its own output_config/effort, its own usage dict with the cache fields at :632-643); graph/resolution.py:420-475 ClaudeAdjudicator (anthropic.Anthropic() at :445 with no timeout and default retries, its own effort/output_config, usage summed by hand at :467-469); parsers/vision.py:101 + :184-206 (fourth client, hand-built image message, the only caller of ml.usage.record). Choosing a backend by spec.kind is also repeated: extraction.current (:824), ask.answerer_for (:562), steps/graph.py:332-345, vision.read (:166-182).
- **Evidence.** ml/usage.py says every client of a paid model must record its use so the worker can carry it home, but only vision.read does (grep 'usage.record' finds one caller). Reading steps call runtime.chat and throw the usage away: parsers/formulas.py:151 (`out, _usage = runtime.chat`), parsers/polish.py:105, writing/genres.py:240, graph/communities.py:216. When steps.formulas or steps.polish names a Claude model, models.runtime returns ClaudeRuntime, which never records, so steps/parse.py:243-251 posts no spend for those readings. The budget ledger then undercounts in the way the 2026-09-23 incident in usage.py's docstring describes. ClaudeRuntime also returns no cache tokens, so pricing undercounts cached prompts on every step that goes through it.
- **Why here.** The next bug is the next Claude step: whoever adds it picks one of the four shapes, and three of them leave the ledger blind. The timeouts and retries also differ per site: the adjudicator can hang with no timeout.
- **Fix.** Make ClaudeRuntime the one owner. Give chat() options for `schema=` (json_schema output_config), `images=` (as OpenAIRuntime already takes), `cache_system=True` and `effort`, have it return the full usage including the cache fields, and have it call ml.usage.record itself. ClaudeExtractor.params/extract, ClaudeAdjudicator.decide and vision.read's Claude branch then become one call each, and vision._client goes. The batch path's params() can call a `ClaudeRuntime.params()` that chat() also uses.
- **Risk.** The extractor's batch path (it reuses params()) and the prompt-cache prefix must stay byte-identical, or caching stops. Recording in the runtime could double-count wherever a caller also forwards the returned usage to the ledger (extraction posts usage in its result), so record in one of the two places, not both.
- **Checked.** Confirmed. ClaudeRuntime.chat (models.py:747-783) keeps only input/output tokens and never calls ml.usage.record; ml/usage.py:1-15 says every paid client must record, and grep finds a single caller (parsers/vision.py:205). formulas.py:151 and polish.py:105 discard usage, and steps/parse.py:244-251 posts only what usage.take() (steps/parse.py:452) collected. So a Claude-backed formulas or polish reading leaves no ledger row. That is the 2026-09-23 failure again. There are four client builders: models.py:763 (timeout and 3 retries), extraction.py:589, resolution.py:445 (bare anthropic.Anthropic(), no timeout) and vision.py:101. The token-reading code differs too: resolution sums three fields and drops cache_creation. The one-owner fix holds. ~60 lines is more realistic than 90, because the batch params path keeps its own shape. Risk: the extractor's batch path and budget tests.

### 6. A model's reading under a marked line is implemented twice (figures, formulas), and only figures' readings survive a re-read

*high, logic; half a day, with a test that a formula reading survives a replacing read; about 50 lines.*

- **Sites.** parsers/figures.py:1065-1146 describe and parsers/formulas.py:118-170 describe follow the same algorithm: a mode setting validated against WHICH (figures.py:1079, formulas.py:125-132), refs() that lists who read each one (figures.py:823, formulas.py:57), around() (figures.py:915, formulas.py:86, nearly identical), _read_by (figures.py:971, formulas.py:113, identical), whitespace collapse, delete this model's earlier line and insert `*X, as read by who:*` (figures.py:1130-1141, formulas.py:159-167), and raise when none was read. formulas.py also reaches chunking's private names (chunking._READ_BY, chunking._is_formula at :65, :67, :93-94, :162). figures.carry_readings (:1011) carries only figure readings.
- **Evidence.** carry_readings keys readings by `_figure_ref_of(line)`, which matches only `(figure:<sha>)` lines, so `*Formula, as read by …*` lines are not carried by parsers/queue.py:256 or store/repair/documents.py:786/811 when a replacing read (marker, OCR) writes a new text. That is the 2026-10-06 failure carry_readings was written for, still open for formulas, and the last commit asked for 305 formula readings.
- **Why here.** The plan keeps adding readings (crops, formulas, AD2's equation step in the maths pack). Each new kind repeats the same 60 lines and quietly misses the carry-over, and that loss shows up only after a marker evening.
- **Fix.** Add one `parsers/readings` core: `annotate(lines, anchors, who, again, read_one) -> text` and `carry(previous_texts, text, anchor_of)`, where an anchor is a function from a line to a key (figure ref or formula LaTeX hash). figures and formulas each supply their anchor, prompt and model call. Use markup.read_by to write the line and markup.READ_BY to match it.
- **Risk.** Moderate: the order of readings under a figure and the `again` replacement are tested behaviour (test_markup, test_chunking). Keying formulas by LaTeX means a re-read that changes the LaTeX drops the reading, which is acceptable.
- **Checked.** Confirmed. formulas.describe (:118-170) repeats figures.describe's algorithm: mode check against WHICH, refs, around, an identical _read_by (figures.py:971 and formulas.py:113), delete the model's own earlier line, insert the hand-written line. formulas.py reaches chunking._READ_BY and chunking._is_formula (private) at :65, :67, :93-94 and :162. carry_readings (figures.py:1011) keys only on _figure_ref_of (:1003), which matches figure lines only. Its callers are parsers/queue.py:256 and store/repair/documents.py:786 and :811. A replacing read therefore drops every '*Formula, as read by*' line, and only _unread_formulas (repair/documents.py:351) asks for them again, at model cost. A shared annotate/carry core with an anchor function holds up. Caveat: marker rewrites the LaTeX, so a formula anchor keyed on a LaTeX hash may carry less than a figure's sha does. ~50 lines.

### 7. retitle re-implements entity rename and merge, bypassing store.graph.labels

*high, concepts; an hour plus a test; about 15 lines.*

- **Sites.** 1 copy (meta.py:416-443) of 2 owners: labels.rename_entity (labels.py:613) and labels.merge_entities (labels.py:36). It is the only writer of entities.name / canonical_id outside graph.labels (graph/naming.py:474 is the other raw name write).
- **Evidence.** retitle writes `UPDATE entities SET name = ?` and `UPDATE entities SET canonical_id = ? WHERE id = ? OR canonical_id = ?` itself. merge_entities also writes the duplicate's name as a label, merged_by and merged_run (migration 25) and merge_moves for undo; _refresh_name keeps the replaced name as a label before overwriting it. The copy does none of that. It exists because `documents` comes before `graph` in the store ORDER, so it cannot import labels at module level.
- **Why here.** CLAUDE.md says entities.name is a cache rebuilt from labels by the `names` pass, and that a merge carries its stamp so unmerge_run can undo it. A rename made by retitle has no label, so the next names pass can rebuild the old name over it. A merge made by retitle has no run, so nothing can take it back. Stratification step 5 (name becomes a display label) has to find this second writer too.
- **Fix.** In retitle, call the labels functions from inside the function (the documented 'call up inside a function' route), or let the door handler compose retitle with labels.rename_entity / merge_entities(producer='retitle', run=run). Delete the inline SQL. Add a test: retitle onto an existing paper title, then unmerge_run puts it back.
- **Risk.** retitle's result dict (`entity_action`) and the shared-title guard must stay the same. merge_entities raises on cross-type and cyclic merges, which the copy silently skipped, so the call needs a try/except that keeps today's 'no action' answer.
